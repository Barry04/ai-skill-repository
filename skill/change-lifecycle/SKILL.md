# 需求生命周期与兼容边界

让需求从首次开发到自测修复持续保留上下文。兼容义务取决于真实调用方、数据和发布证据，不取决于代码是否已经存在或上一轮是否结束。

## 先关联，再修改

1. 查找项目已有的需求单或变更记录，按用户指定编号、目标和修改范围关联；分支与最近文件只作辅助。归属不唯一时问一个具体问题，继续不依赖答案的探索。
2. 没有记录且已获准实施时，自动从对话和代码中补建最小记录，无需用户额外说“记录需求”。优先沿用项目位置；无约定时用 `docs/changes/YYYY-MM-DD-<slug>.md`，参考 [记录模板](assets/change-record.template.md)。只读、纯问答或明确禁止落盘时，仅在回复给草案。
3. 填写目标、范围、开发起点、阶段和已知依赖。已有手写或未提交改动也纳入范围说明，保留原内容；起点 SHA 不等于生产基线，也不能代表本需求之外的所有差异。
4. 设计确定、实现完成、自测反馈、发布反馈后，更新同一份记录。用户“不想额外维护文档”由 Agent 负责维护；用户明确“不要创建文件”则遵守不落盘要求。

首次建记录和处理发布事实时，读 [状态与证据约定](references/record-and-evidence.md)。已有需求系统能保存这些信息时直接使用，不再复制一套事实源。

## 分开维护进度与事实

- 实现与本地检查完成 → `awaiting_self_test`；收到该需求的自测问题 → `self_test_fix`；修复后回到待自测。
- 发布情况、外部调用方、数据保留要求分别记录 `unknown` 或有依据的结论。未找到证据不等于“没有依赖”；缺少发布信息保留未知，不写成“尚未发布”。
- 提交、合并、测试通过、部署自测环境或上一轮“完成”，均不能单独证明已发布或必须兼容。发布事实注明来源、版本/范围和时间；新证据与旧记录冲突时先核实更新。

## 每次修改的兼容决定

| 已确认的事实 | 本次处理 |
| --- | --- |
| 本轮新增实现，调用方和数据均无保留义务 | 直接修正定义、调用和测试，删除废弃路径；不为原错误实现增加双读、双写、别名或 fallback |
| 有已发布调用方、联调依赖或需保留数据 | 保护具体依赖，协调调用方/迁移；必要兼容写明对象、证据及可观察的移除条件 |
| 信息不足或记录冲突 | 查部署/调用/数据依据；只对影响当前决定的缺口提问，不推测已发布或未发布 |

判断限于本次接口、字段或行为。旧项目里的新需求仍须保护既有生产契约；自测环境也可能有联调方、持久数据或已执行迁移。调整已执行迁移的原文件不会自动更新现有数据库，不能据此清库或重建环境。

回滚、关闭功能开关后也要检查已产生的数据、旧客户端和在途请求，不能把曾经产生的依赖自动清零。记录和本 Skill 本身不授予发布、清库、跨项目改配置或安装全局规则的权限。

## 收尾与接入

收尾说明：记录位置/编号、当前阶段、本次兼容决定及依据、验证结果、仍未知且影响后续的事实。方案、拟执行命令和实际结果分开写，不自称做过未执行的测试或发布。

例：同一需求的 `type` 仅在自测使用，用户确认无独立调用方且数据无需保留，则统一改为 `category` 并删除旧读取路径；记录留在待自测。已有客户端依赖 `type` 时另行保留有依据的兼容。

需要在项目中稳定触发时，将 [入口规则片段](assets/agents-rule.md) 合并到获准修改的项目 `AGENTS.md`。仅安装 Skill 不保证每次自动触发；不要借接入之名修改无关项目或全局配置。一次性需求记录不生成新的可复用 Skill。
